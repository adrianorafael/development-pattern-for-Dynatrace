# Git & publishing — the repository flow

> Rules **R1** (no secrets), **R10** (no AI co-authorship), **R11** (naming convention).

---

## R11 — Naming

**`<App Name> for Dynatrace`.** Everywhere the app is named publicly:

| Where | Value |
| --- | --- |
| GitHub repository | `Command-Center-for-Dynatrace` |
| README `# H1` | `# Command Center for Dynatrace` |
| Page `<title>` and hero | `Command Center for Dynatrace` |
| GitHub Pages URL | `https://<user>.github.io/Command-Center-for-Dynatrace/` |
| `app.config.json` → `app.name` | `Command Center` — the in-product menu label, **without** the suffix |
| `app.config.json` → `app.id` | `my.command.center` |

The suffix is for the outside world; inside Dynatrace the platform already supplies the
context, and "Command Center for Dynatrace" in the Dynatrace app menu reads as a stutter.

## R10 — No AI co-authorship

**Default: the human is the sole author.** Unless the user explicitly asks for it, nothing
that reaches the repository mentions the AI.

Never in a commit message, PR title/body, README, page, code comment, or changelog:

- `Co-Authored-By: Claude …` or any AI co-author trailer
- `🤖 Generated with [Claude Code]` / `Generated by …` footers
- Session links back to an AI tool
- "AI-assisted", "written by an agent", "vibecoded with…" — unless *the user wrote that*

Check before every commit — some tooling appends trailers automatically:

```bash
git config user.name && git config user.email     # must be the user's identity
git log -1 --format='%an <%ae>%n%n%B'             # inspect the full message
git log -1 --format='%B' | grep -iE 'co-authored-by|generated with|claude|anthropic|🤖'
```

If a trailer slipped into the most recent, unpushed commit:

```bash
git commit --amend --no-edit --reset-author
# or rewrite the message explicitly:
git commit --amend -m "feat: add problem status cards"
```

**If the user does want the attribution**, add exactly what they ask for, nothing more.

## Repository setup

Phase 0 established whether one exists. Then:

```bash
# existing
git remote add origin https://github.com/<user>/<App-Name>-for-Dynatrace.git

# new — confirm public vs private with the user FIRST; it changes the secret calculus
# (a private repo is not a safe place for a token either — it just leaks to fewer people)
```

Before the first commit, always:

1. `.gitignore` in place and verified — [security-and-secrets.md](security-and-secrets.md)
2. `LICENSE` — ask which; MIT and Apache-2.0 are the usual answers
3. `README.md` — [readme-and-page.md](readme-and-page.md)
4. `.env.example` committed, `.env` ignored
5. `AGENTS.md` pointing future agents at this skill

## The commit flow

**Never `git add -A` blind.** Look at what you are staging.

```bash
# 1. See everything that would go in
git status
git diff

# 2. Secret scan — working tree
bash skills/development-pattern-for-dynatrace/assets/scripts/scan-secrets.sh

# 3. Stage deliberately
git add app.config.json ui/app/pages/Problems.tsx

# 4. Secret scan — the staged content, which is what actually ships
git diff --cached | bash skills/development-pattern-for-dynatrace/assets/scripts/scan-secrets.sh --stdin

# 5. Review the staged diff one more time
git diff --cached

# 6. Commit
git commit -m "feat(problems): add status filter cards"
```

Any hit in step 2 or 4: **stop, sanitize, rescan.** Do not commit "and clean it up next".

### Commit messages

Conventional Commits, imperative, scoped:

```
feat(problems): add auto-refresh toggle with 5-minute default
fix(charts): convert Grail timestamps to Date before TimeseriesChart
docs(readme): add DPS consumption estimate
chore(deps): bump @dynatrace/strato-components to 3.11.3
```

The body explains **why**, and names the cost or security consequence when there is one:

```
feat(problems): default auto-refresh to off

Auto-refresh runs one Grail query per minute per open tab, which is the
dominant DPS cost driver. Defaulting it off makes the cost opt-in.
```

Never in a message: tenant URLs, tokens, real customer names, AI attribution.

## The push flow ⛔ approval gate

**Ask before every push.** Not once per session — every push.

> Ready to push 3 commits to `origin/main`:
> - `feat(problems): add status filter cards`
> - `fix(charts): convert timestamps to Date`
> - `docs(readme): document the new filter`
>
> The sanitize pass replaced the tenant URL in `app.config.json` with
> `YOUR-ENVIRONMENT`. Secret scan is clean. Push?

Then:

```bash
git push -u origin <branch>
```

On network failure, retry up to 4 times with backoff (2s, 4s, 8s, 16s). On an
authentication or permission failure, **stop and report** — do not try another remote,
another credential, or another branch.

### Branching

- Feature work on `feat/<slug>` or `fix/<slug>`; merge to `main` when reviewed.
- Solo demo repos may commit to `main` directly — confirm that is what the user wants.
- **Never force-push a shared branch.** On your own branch, and only when the user asked.
- Never push to a branch the user did not name.

---

## Pull requests

**Only when the user asks for one.** A push is not a PR request.

When they do ask: check for a template (`.github/pull_request_template.md`,
`.github/PULL_REQUEST_TEMPLATE.md`, root, or `docs/`) and mirror its headings. No AI
attribution footer (R10) unless the user wants it. Never paste tenant URLs, tokens or real
data into the body — describe the change, not the environment.

## Publishing the repository

For a public app repo, the full standard:

| Item | Detail |
| --- | --- |
| Name | `<App-Name>-for-Dynatrace` (R11) |
| Visibility | Public — confirm with the user |
| README | The house standard → [readme-and-page.md](readme-and-page.md) |
| GitHub Pages | `main` branch, `/docs` folder → same reference |
| LICENSE | User's choice |
| Topics | `dynatrace`, `dynatrace-app`, `appengine`, `strato`, `dql`, `grail` |
| Description | One line, matching the README's opening |
| Secret protection | *Settings → Code security → Secret protection → Push protection* — recommend it |

**Enabling GitHub Pages requires the repository owner.** It cannot be done from a commit.
Tell the user the exact clicks:

> *Settings → Pages → Build and deployment → Source: **Deploy from a branch** →
> Branch: `main`, Folder: `/docs` → Save.* The site appears at
> `https://<user>.github.io/<Repo-Name>/` within a minute or two.

---

## Keeping the repository current

Each time the user agrees to push, in this order:

1. **Sanitize + scan.** Every time.
2. **Code.** The change itself.
3. **Spec.** If behaviour changed, the spec changes in the same commit.
4. **README.** If setup, scopes, features or **cost** changed, the README changes too.
5. **Page.** `docs/index.html` mirrors the README's substance — do not let them drift.
6. **Version.** Bump `app.config.json` → `app.version` for anything deployable.

A README that describes last month's app is a bug report waiting to happen.
