The problem

Vibecoding a Dynatrace App works — until it doesn't

Four failures show up in almost every AI-built Dynatrace App. None of them announce themselves; all of them cost hours.

🧪

Invented APIs

A component prop recalled from training data rather than read from the package. It compiles, renders nothing, warns about nothing.

Fixed by R2 — verify against .d.ts, every time
🎨

Foreign design

Tailwind classes, a Recharts line chart, a hardcoded #1496ff. The app stops looking native and breaks in dark mode.

Fixed by R3 — Strato only, tokens only
📉

Silent empty charts

Grail records handed straight to a chart that wanted a different shape. No error, no data, no clue.

Fixed by R7 — convert, assert, then render
🔓

Leaked tenant data

A tenant URL in app.config.json, a token in .mcp.json, .dt-app/ committed with cached OAuth tokens.

Fixed by R1 — placeholders, gitignore, scanner
The contract

Twelve non-negotiable rules

Stated as absolutes on purpose. "Prefer Strato where reasonable" becomes, in practice, "use Strato until something is mildly inconvenient".

#RuleWhat it stops
R1Never publish a secret. No tokens, .env, tenant IDs or URLs, emails, customer names. Placeholders instead.A leaked credential you must rotate
R2Never invent an API. Every component, prop, icon, hook, DQL function and CLI flag verified against node_modules/**/*.d.ts or the docs, in-session.Props that silently do nothing
R3Strato only. No MUI, Ant, Chakra, Tailwind, Recharts, Chart.js, ECharts or raw D3.An app that doesn't look native
R4Research before spec. Read the section and follow its links. Never answer from memory alone.Designs built on an overview's depth
R5Spec before code, with an explicit approval gate.Six rounds of correcting symptoms
R6Every DQL is executed against a live tenant before it ships.Queries that return nothing in prod
R7Every visualization is fed a verified data shape — converted, asserted, then rendered.Blank charts with no error
R8No monotonous screens. Chart type follows the data's shape and the question, not habit.Five line charts answering nothing
R9Review AI-written code like hostile code, against a security and quality checklist.Fluent code that is quietly wrong
R10No AI co-authorship in commits, PRs, README, page or comments — unless you ask for it.Attribution you didn't want
R11Naming convention <App Name> for Dynatrace for repository, README, page and Hub listing.Inconsistent public identity
R12The version and the docs move with the app. Every publication bumps app.version per SemVer; every push that changes behaviour, setup or cost updates the README and this page in the same commit.Docs nobody trusts, versions that mean nothing
The workflow

Six phases, three hard gates

No spec without research. No deploy without a named target. No push without a sanitize pass.

0 BOOTSTRAP   repo? tenant? MCP? identity? publication?  → official skills installed, .gitignore armed
1 RESEARCH    developer.dynatrace.com, depth-first       → evidence log with URLs actually read
2 SPEC        specs/<slug>.md                            → ⛔ USER APPROVAL GATE
3 BUILD       Strato-only, verified APIs                 → every symbol traced to a .d.ts or a doc page
4 VALIDATE    DQL on live tenant + data-shape assert     → real records shown to you
              + lint + security & quality review
5 RUN/DEPLOY  dt-app dev → dt-app deploy                 → ⛔ USER APPROVAL GATE before deploy
6 PUBLISH     bump version → CHANGELOG → README + page   → ⛔ USER APPROVAL GATE before push
              → sanitize → commit → push → tag
Phase 0 asks five questions in one batch — repository, target tenant, MCP availability, app identity, publication intent — and every later decision refers back to those answers instead of re-asking.
Under the hood

How each rule is actually enforced

The reference documents load on demand, before the work — not after it fails.

🔵 Verification beats recall

Before writing <HoneycombChart>, the agent greps charts/index.d.ts. Before writing a prop, it reads the component's own .d.ts. Every claim lands in an evidence log with its source.

🟢 Depth-first documentation

One page is a table of contents, not an understanding. The protocol requires following in-page links into foundations, patterns and guides, then cross-checking the API against the installed package.

🟣 DQL is executed, not reasoned about

Built in layers — fieldsSummary to discover real fields, filter, shape, confirm with you, record the scanned bytes. Without MCP, queries are labelled ⚠️ Unvalidated rather than quietly trusted.

🟡 Data contracts, then rendering

Charts take a unified ChartData flat array with accessor strings; TimeseriesChart wants datapoints[].start as a real Date. The agent prints the actual data, asserts the contract, then looks at the rendered screen.

🔵 Anti-monotony test

A screen is checked for a headline layer, bars for categories, rankings as a TopList, at most one pie. But variety is never the goal — fit is: three genuinely different time series stay three line charts.

🟣 Nothing is vendored

The skill carries no copy of the Dynatrace docs or of Dynatrace's own agent skills — only their URLs, opened live during the session. A copy taken last week looks authoritative while being wrong, so there is no copy to go stale.

🟢 Sanitize, then commit

scan-secrets.sh runs over the working tree and the staged diff, catching Dynatrace tokens, tenant URLs and IDs, entity IDs, private keys and hardcoded credentials — plus structural checks for tracked .env and .dt-app/.

R12

Release & docs sync

The version and the documentation are part of the change, not follow-up work. A commit that changes behaviour without bumping the version and updating the docs is an incomplete commit.

Semantic versioning, in app terms

"Breaking" means breaking for the person running the app — not for a library consumer.

  • MAJOR — a scope changed (everyone re-consents) · persisted state format changed without migration · a feature removed · a default that raises cost
  • MINOR — new view, chart, filter or setting; nothing existing breaks
  • PATCH — bug fix, copy, styling, dependency bump, query optimized with identical results
A demonstration app belongs on 0.x. Reaching 1.0.0 is a claim about stability — don't make it by accident.

Three rules that make a version trustworthy

  • Never publish the same version twice — once a build reaches a tenant, that version is spent
  • Bump in the same commit as the change, never in a separate "bump" commit
  • Tag what you publish: git tag -a v1.2.0
The one people get wrong: adding an OAuth scope is MAJOR — every existing user hits a consent screen on next load, however small the diff.

The README and the page are one document at two depths. They must agree on the disclaimer, the scopes, the cost figures, the troubleshooting rows and the version. Divergence is invisible until a reader notices the page promises a feature the README has never heard of.

Get running

Install & use

Works with any agent that supports the open Agent Skills format.

Prerequisites

  • An agent supporting Agent Skills — Claude Code, Cursor, Copilot, OpenCode, Gemini CLI
  • Node.js ≥ 18 and npm ≥ 9 for dt-app
  • A Dynatrace environment with Grail
  • Recommended: the Dynatrace MCP server or dtctl, so DQL can be validated
  • Network access to developer.dynatrace.com, docs.dynatrace.com and GitHub

The Dynatrace docs are referenced, not bundled

This skill covers how to build and publish an app. Dynatrace's own skills cover what the data means — DQL semantics, Grail entities, costs. It ships no copy of them: they change between your sessions, and a stale copy looks authoritative while being wrong. It fetches the file it needs, when it needs it.

Works best where developer.dynatrace.com, docs.dynatrace.com and GitHub are reachable — i.e. your editor.
# Skills package (recommended)
npx skills add adrianorafael/development-pattern-for-Dynatrace

# Claude Code plugin
claude plugin marketplace add adrianorafael/development-pattern-for-Dynatrace
claude plugin install development-pattern-for-dynatrace@development-pattern-for-dynatrace

# Manual — copy into your agent's skills path
git clone https://github.com/adrianorafael/development-pattern-for-Dynatrace.git
cp -r development-pattern-for-Dynatrace/skills/development-pattern-for-dynatrace \
      .claude/skills/development-pattern-for-dynatrace

Connect it to a tenant so DQL can be validated (R6):

# .env — gitignored. Real values live ONLY here.
DT_ENVIRONMENT=https://YOUR-ENVIRONMENT.apps.dynatrace.com
DT_PLATFORM_TOKEN=dt0s16.YOUR-PLATFORM-TOKEN
// .mcp.json — committed, with ${ENV} references, never literal values
{
  "mcpServers": {
    "dynatrace": {
      "type": "http",
      "url": "${DT_ENVIRONMENT}/platform-reserved/mcp-gateway/v0.1/servers/dynatrace-mcp/mcp",
      "headers": { "Authorization": "Bearer ${DT_PLATFORM_TOKEN}" }
    }
  }
}
Replace YOUR-ENVIRONMENT with your own tenant ID — the URL has the form https://<tenant-id>.apps.dynatrace.com, copied from your Dynatrace address bar. Grant the platform token the minimum scopes for the queries your app runs. Without MCP the skill still works; it just labels unvalidated queries as such.

Then simply ask for an app. The skill triggers on its own when you mention a Dynatrace App, dt-app, Strato, AppEngine, DQL or Grail.

Cost awareness

Cost & consumption (DPS)

The skill itself costs nothing. The apps it helps you build do — and the pattern treats that as a design constraint, not an afterthought.

Cost driverImpactNotes
Auto-refreshDominant One Grail query per interval, per open tab. The single biggest lever.
Timeframe widthMedium Wider window = more data scanned per run.
Concurrent users / tabsLinear Each open instance runs its own refresh loop.
Projected fieldsReducible Grail is columnar — | fields … scans fewer bytes.

Illustrative monthly scenarios for a typical app built under this pattern

ScenarioQueries / monthGB scanned*Est. cost**
Auto-refresh OFF, 5 users, manual use~2,000~2 GB Negligible
Auto-refresh ON (1 min), 5 users, 8h/day~53,000~260 GB Low–moderate
Auto-refresh ON (1 min), 20 users, 8h/day~211,000~1 TB Watch this

* Assuming ~5 MB scanned per query in a busy environment; small environments scan well under 1 MB. ** Multiply GB scanned by your contract's "Grail Query – data analyzed" rate — the dollar amount depends entirely on your rate card, so measure before relying on estimates.

What the pattern requires

  • A cost section in the spec, before the code exists
  • Filter-early, project-only-needed-fields queries
  • Auto-refresh off by default, or a defensibly slow interval
  • A Query Cost & Consumption (DPS) section in every app's README and page

Measure it precisely

  • Run the query in a Notebook and read metadata.grail.scannedBytes from queryExecute
  • Confirm aggregates in Account Management → Cost & usage → Grail Query
The estimate is a starting point. Your rate card is the answer.

Help

Honest answers

QuestionAnswer
Does it work without the MCP server? Yes — but it cannot satisfy R6, so every query it writes is labelled ⚠️ Unvalidated and you are told to verify it in a Notebook.
Is the Strato component inventory guaranteed accurate? No. It is a snapshot of @dynatrace/strato-components@3.11.3 from August 2026, included to speed up lookups. The skill's own instruction is to re-verify in your project's node_modules.
Will the scanner catch every secret? No. It catches known patterns. A secret that looks like ordinary text will pass. A clean scan is necessary, not sufficient — read your own diff.
Can I disagree with a rule? Yes. It is Markdown, and it is yours — edit SKILL.md. The rules are absolutes because soft preferences erode under deadline pressure, not because they are sacred.
Why does the agent ask more questions than before? Because R2 forbids guessing. When a package isn't installed and the docs are unreachable, the skill's instruction is to say so and offer two unblocks rather than emit a plausible-looking prop.
Does it bundle the Dynatrace documentation? No, deliberately. It carries URLs — every design, components, data-visualization, icons, patterns, foundations, AppEngine, guides, security and code-optimization page — and opens them live during the session. Nothing to go stale, nothing to re-sync.
Why does it insist on bumping the version? Because three deploys all reporting 1.0.0 make it impossible to tell which build is running in which tenant. The bump, the CHANGELOG entry and the doc updates land in the same commit as the code.
Is this official Dynatrace tooling? No. It is an independent, unaffiliated project. Dynatrace's own agent skills live at Dynatrace/dynatrace-for-ai, and this skill routes to them.
